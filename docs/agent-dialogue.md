# Составные вопросы, обзор объекта и контекстные уточнения

## Исправленный случай

В диалоге 12 ноября просьбы «расскажи всё о железе» и «все сведения и связанные вещества» сводились к короткой карточке `element`: Fe и 26. Агент принимал её за достаточный результат, а проверка снимка подтверждала числа без контроля остальных частей вопроса.

Теперь:

- Вопрос о возможностях обрабатывается по доступным MCP-инструментам и выбранным путям, без просьбы сначала назвать марку/элемент и без генерации LLM.
- Для широкого запроса используется `query_knowledge` с `operation=overview`. Краткая карточка `element` сохраняется для точечных вопросов.
- Обзор проверяет карточку и связи по всем выбранным ресурсам данных. Выделены вещества, материалы и другие объекты. Нулевой результат связи показывается явно; недоступность базы не превращается в утверждение об отсутствии связей.
- Перед завершением проверяются распознанные части составного вопроса. Преждевременный `finish sufficient=true` отклоняется с указанием пробелов. При исчерпании шагов возвращаются проверенные сведения с явным списком невыполненных частей.
- Сверка данных со снимками и выполнение частей вопроса показываются раздельно, в том числе для исторических ответов без контроля частей. Это не универсальное доказательство правильности понимания языка: поддержанные фасеты выделяются приложением по распознаваемым типам запросов, `meaning_verified` остаётся false.

## API обзора

```json
{"operation":"overview","subject":"Fe","entity_meta":"Химический элемент","overview_sections":["attributes","substances","materials","other"],"limit":5}
```

`subject` — точное имя/обозначение. `entity_meta` уточняет тип, если в базе существуют разные объекты с одинаковым именем. Поддержаны элементы, вещества, материалы, классы материалов/свойств, свойства и термины. Упоминание Fe внутри состава не считается самостоятельной карточкой элемента. При неоднозначности агент должен уточнить объект.

`overview_sections` выбирает части ответа: атрибуты, вещества, материалы, другие связи. Запрос только о веществах не повторяет все материалы. Результат содержит `entity`, `attributes`, `attribute_total`, `related`, `sections`, `rows`, полные количества, ссылки и источники. Списки связей разбиты на страницы; `has_more`/`next_offset` сохраняют условия при продолжении. Атрибуты показываются до `limit`, их полное количество обозначено отдельно.

Связи вычисляются по данным: компонентам состава, точным названиям/обозначениям, ID/original_id и обозначениям химических формул. Формулы с Unicode-индексами обрабатываются через NFKC; C не смешивается с Co. Вывод содержит основание каждой связи. Указание Fe в составе включает примеси и ограничения с нулевой нижней границей: это не утверждение о ненулевом содержании каждой партии. Текстовые намёки и неописанные связи не превращаются в химические факты.

Онтологии с названием «Онтология…» не используются как карточки объектов. Схемы могут исследоваться отдельно через `structure`. Ничего не дополняется энциклопедическими сведениями из памяти модели: если в базе у железа только два атрибута, приложение сообщает об этом и показывает найденные связи.

## Память диалога

Структурированный план предыдущего хода хранит объект и условия. Для однозначного уточнения «а какие связанные вещества?» приложение получает новый результат MCP по уже известному объекту и нужному разделу; старый текст ответа не используется вместо данных. Аналогично продолжаются страницы предметных списков. Это обработка контекстной команды, а не заготовленный ответ: значения и связи каждый раз рассчитываются по данным.

Явно названный новый объект не подменяется предыдущим. После перехода к другому предметному запросу приложение не извлекает устаревший объект из глубокой истории. Если контекста недостаточно, остаётся обычное планирование моделью/уточнение.

## Проверки 12 ноября 2026

На подключённой базе через чтение MCP: у Fe два атрибута, Fe указан в составах **1323 материалов**, подтверждённых веществ с Fe в проверенной базе не найдено. Подсчёт выполнен по полным графам, а не показанным строкам, и повторно сверён с SHA-снимками. Это результат конкретного состояния данных, а не зашитые ответы.

Реальная локальная Qwen с историей проблемного диалога выполнила обзор и закрыла обе распознанные части. Первое узкое уточнение выявило попытку использовать старый текст без новых источников; после исправления контекстного исполнения уточнение выполнило свежий MCP-запрос без генерации, без повторения карточки/материалов и с явным `no_matches` для веществ.

Тесты также проверяют другие элементы, формулы, материалы и классы, неоднозначные имена, лимиты страниц, отказ одной базы, составные вопросы «структура + количество вершин», сохранение явных фильтров и неполные ответы. Локальные диагностические отчёты находятся в ignored `logs/overview-real-data.json`, `logs/coverage-live-results.json`, `logs/coverage-followup-fixed.json`; пользовательские диалоги не изменялись. Живая запись и платные API не использовались. Модель после диагностического запуска возвращена в исходное выгруженное состояние.
